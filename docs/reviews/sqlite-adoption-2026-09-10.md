## Applicability of the absent fixes

The absent fixes separate into damaged-file handling and other conditional surfaces. None of them is a demonstrated healthy-write corruption path. The distinction between a demonstrated effect and possible exploitability is preserved below.

Damaged-file handling is the material gap. `6826c17021` and `1a888ea60b` harden index-page and freelist reads against already damaged database pages. These are reachable with ordinary SQL once a file on disk is damaged, independent of user-supplied SQL shape. The [differential probe](evidence/sqlite-adoption-2026-09-10/differential-probe.json) demonstrates the `6826c17021` effect directly: a database with one text row and one index, on a 512-byte page, with a single index-cell payload-length byte inflated from 4 to 100, returns the row from an indexed `SELECT` under 3.53.2 and returns `SQLITE_CORRUPT` under 3.53.3 and 3.53.4. This establishes a missing rejection on a damaged file. It does not establish memory disclosure, exploitability, or a mechanism by which healthy writes produce the damage. `PRAGMA integrity_check` reports the damage in all three builds, naming the page and cell; the successful integrity check in the readiness probe tested a healthy database only and does not make integrity_check a complete safe parser for arbitrary damaged files.

The remaining four fixes are conditional and not demonstrated here. `9471fa2c9c` is a file-deletion trust boundary that matters only if untrusted files can enter the database directory or be restored or imported as database state; ordinary prompt text bound into SQL does not create the required file structure, and private application-created state reduces the threat substantially without eliminating it for future import or restore. `9a79ca31ff` is conditional on a read-only WAL with an uninitializable shared-memory path and damaged WAL data, not on ordinary writable recovery; the owner permits offline diagnostics to report that deeper validation could not safely run, as recorded under [Owner decisions recorded](#owner-decisions-recorded). `aa756c8038` triggers only with a custom VFS whose `mxPathname` exceeds the small-page buffer assumption; the stock Unix VFS uses `mxPathname` 512 and is outside the trigger. `bf70dadc2d` does not apply to the candidate at all, as established above.

The September 9 assessment's broader classification of the full branch interval, including SQL-correctness, FTS, RTREE, JSONB, backup, and URI-parsing changes, still holds: their presence in the amalgamation is not evidence that ordinary bound-text insertion reaches them, and they require a query and feature audit when actual storage SQL is proposed. Nothing in this record selects storage SQL or features.

## Route comparison

Facts for each route are in [route-comparison.json](evidence/sqlite-adoption-2026-09-10/route-comparison.json). Costs below are dependency, distribution, and ongoing maintenance.

**Accept the bundled candidate (rusqlite 0.40.2 / libsqlite3-sys 0.38.2, SQLite 3.53.2).** Dependency cost is lowest: two exactly pinned crates already reviewed for source correspondence, with the bundled amalgamation compiled from crate-internal source. Distribution cost is lowest: the amalgamation compiles as part of the normal crate build on all four targets with no external library. Maintenance cost is a standing native-fix gap: the adopter carries the absent damaged-file hardening (`6826c17021`, `1a888ea60b`) and the conditional fixes until a later crate release, and must accept those residual risks explicitly. Residual risk is the demonstrated index-bounds acceptance on damaged files plus the conditional recovery and file-deletion surfaces above.

**Wait for a crate release bundling 3.53.4.** Dependency and distribution cost are identical to the bundled candidate once such a release exists, and the native gap closes. The cost is schedule uncertainty: no crate release currently bundles 3.53.4, and on 2026-09-10 UTC there is no open milestone, pull request, or issue signaling a planned or imminent release. The last release, v0.40.2, is dated 2026-08-08; master is three commits ahead of it and carries the 3.53.4 bump. A release is plausible but unscheduled, and its timing is outside `ask`'s control.

**Pin a rusqlite git commit (master, SQLite 3.53.4).** This closes the native gap now. Its costs are policy and provenance rather than tracking: `deny.toml` sets `unknown-git = "deny"`, so a git source needs an explicit policy exception approved by the owner; the pinned commit is not a published, checksummed registry artifact, so its provenance must be reviewed directly; the commit carries unreleased rusqlite changes beyond the SQLite bump; and every later move to a newer commit or back to a registry release is a deliberate, reviewed update. A commit pin does not follow the moving branch, and a locked build does not require vendoring. The mental model does not prohibit a reviewed git pin, but its dependency posture makes the exception an owner decision.

**Non-bundled external-library link (ask-built 3.53.4 amalgamation).** libsqlite3-sys 0.38.2 supports linking an external library through `SQLITE3_LIB_DIR` and `SQLITE3_INCLUDE_DIR`, with `SQLITE3_STATIC` selecting static linking. This lets `ask` compile the official 3.53.4 amalgamation itself and link it through the sys crate without a bundled feature. Dependency cost stays on registry crates, avoiding a git source. Distribution and maintenance cost is high and recurring: `ask` must build and pin the amalgamation for all four supported targets, wire the build and environment into the normal crate build and CI, keep static linkage verified so no dynamic system SQLite leaks in, and re-cut the vendored amalgamation on every SQLite update. This reproduces much of what the bundled feature already does, for the benefit of a version the crate has not yet released.

## Recommendation

Adopt the bundled candidate, rusqlite 0.40.2 with libsqlite3-sys 0.38.2 and SQLite 3.53.2, as the lowest-maintenance practical route, on the strength of the corrected ancestry: the one regression previously feared (`bf70dadc2d`) does not apply, and the genuine gap is damaged-file hardening whose only demonstrated effect is a missing rejection on an already corrupt file, not a healthy-write corruption path. The alternatives close the hardening gap but cost more now: waiting depends on an unscheduled upstream release, a git pin needs a dependency-policy exception, and a hand-built external amalgamation carries high recurring four-target build and maintenance cost to reach a version the crate has not released. Pair adoption with the native-monitoring proposal below so a crate release bundling 3.53.4 becomes a tracked triage item rather than a silent lag.

The narrow owner decision this needed was to accept SQLite 3.53.2 through the bundled candidate with its documented damaged-file hardening gap as an explicit residual-risk acceptance, or to defer adoption until a crate release bundles 3.53.4. The owner took that decision on 2026-09-10; it is recorded in the next section.

## Offline diagnostics and the read-only WAL path

This section answers a question the owner raised on 2026-09-10: whether a read-only `ask doctor` automatically avoids the code path hardened by `9a79ca31ff`, and if not, how an offline diagnostic can avoid both writes and that path. An earlier claim that the read-only flag alone avoids the path was withdrawn; the evidence below replaces it. Every condition is read from the official SQLite 3.53.2 amalgamation (`sqlite3.c`, SHA3-256 `44fd61b9…`) and from the upstream check-in [9a79ca31ff](https://sqlite.org/src/info/9a79ca31ff); function names, line numbers, and the quoted conditions are in [readonly-wal-path.json](evidence/sqlite-adoption-2026-09-10/readonly-wal-path.json), cited here by their `C` identifiers. The Unix VFS is the one read; Windows shared-memory handling differs and was not examined.

**What the fix changes.** The check-in, dated 2026-06-12 and titled "When using a read-only WAL/SHM, handle a corrupt page size in the WAL file correctly", touches only `src/wal.c`. It adds a guard in `walDecodeFrame` that treats a frame as invalid when the connection's page size is zero, before the checksum routine is called with that page size as its byte count, and relaxes an assertion in `walBeginShmUnreliable` so debug builds reach the new guard. The [upstream report](https://sqlite.org/bugs/info/2026-06-11T22:20:03Z) reproduced a heap read overrun with the stock shell opened as `file:…?mode=ro&readonly_shm=1` against a `-wal` file whose header carries page size 0 and a minimal existing `-shm` file. It demonstrates a crash of a read-only process, not a write primitive.

**(a) When a connection reaches the hardened path.** `walBeginShmUnreliable` is called only from `walTryBeginRead` after the connection has marked its shared memory unreliable (C1). That mark is set in one place, `walIndexReadHdr`, only when mapping wal-index page 0 returns `SQLITE_READONLY_CANTINIT`; the connection then rebuilds the wal-index in heap memory (C2). On the Unix VFS that code is returned only when the `-shm` file was opened read-only and no other process holds any lock on its DMS byte (C3). The `-shm` file is opened read-only in exactly two cases: the URI parameter `readonly_shm=1`, or a failed read-write open followed by a successful read-only open, which is what happens when the process cannot write the `-shm` file. If neither open succeeds the result is `SQLITE_CANTOPEN`, not the hardened path, so an unwritable directory with no `-shm` file present does not reach it (C4). The database connection's own `SQLITE_OPEN_READONLY` flag is not consulted when opening the `-shm` (C4). When another process holds a shared DMS lock, a read-only `-shm` is treated as reliable: mapping returns `SQLITE_READONLY`, which `walIndexPage` records as read-only shared memory and converts to success (C5, C6). When another process holds an exclusive DMS lock, which it does while initializing the `-shm`, the lock check returns `SQLITE_BUSY` and `walTryBeginRead` retries; that is not a reliable mapping (C5). A malformed wal-index header in the reliable state yields `SQLITE_READONLY_RECOVERY` rather than recovery only if a shared WAL write lock can be taken; if that lock is busy the busy code is returned instead; in neither case is the hardened function entered (C7). All of this presupposes a WAL connection at all, which exists only when a `-wal` file is present next to the database or the database header's read-version byte is 2 (C11, C12). In the unreliable case the heap wal-index is built by `walIndexRecover` reading the `-wal` file, and `walBeginShmUnreliable` is entered on every read attempt while the mark is set, whatever the `-wal` header contains (C1, C8). The overrun needs more than entry. A `-wal` header with an invalid page size makes recovery finish with an otherwise zeroed header; no code on this path assigns the connection's page size, so a freshly opened connection keeps the zero from its allocation, and `walBeginShmUnreliable` copies the recovered header directly without calling `walIndexTryHdr` again (C8, C9). It then requires the `-wal` file to be at least a header long, the salt bytes in the `-wal` header to match the recovered header's zero salts, and at least one frame header to fit after the `-wal` header before it reads a frame; `walDecodeFrame` requires that frame's salts to match and its page number to be nonzero before it calls the checksum routine with page size 0 as the byte count, which 3.53.2 bounds by assertions only (C9, C10). So the conditions for entering the hardened function are: a WAL connection, a `-shm` the process can open but not write (by permission or by `readonly_shm=1`), and no other process holding a lock on that `-shm`'s DMS byte. The additional conditions for the overrun are a `-wal` file whose header page size is invalid and whose salt bytes are zero, containing at least one frame header with zero salts and a nonzero page number.

**(b) What a read-only open prevents.** `SQLITE_OPEN_READONLY`, or `mode=ro` in a URI, makes the VFS open the database file itself with `O_RDONLY` and sets the pager's read-only flag (C13). It does not change how the `-wal` and `-shm` files are opened: `sqlite3WalOpen` always requests read-write with create for the `-wal`, and `unixOpenSharedMemory` opens the `-shm` read-write with create unless `readonly_shm=1` is set (C12, C4). A read-only connection to a WAL-mode database in a writable directory therefore creates missing `-wal` and `-shm` files, takes read marks in the `-shm`, and runs `walIndexRecover` into the `-shm` when the wal-index header is bad; recovery in that configuration writes shared memory, not the database file. The close-time checkpoint does not reach the database file either: `sqlite3WalClose` calls `sqlite3WalCheckpoint` only after an EXCLUSIVE lock on the database descriptor succeeds, and the Unix VFS takes that lock with a write-lock request, which POSIX rejects on a descriptor not open for writing, so a read-only database connection attempts the lock at close and stops there without reaching checkpoint writes; the checkpoint's own refusal applies only when the `-wal` or `-shm` is read-only (C18). What the flag reliably prevents is SQLite writing the database file through its own descriptor. It neither prevents writes to the side files nor, on its own, excludes the hardened path.

**(c) A hot rollback journal on a read-only open.** For a non-WAL pager, `sqlite3PagerSharedLock` asks `hasHotJournal` whether a journal exists, no RESERVED lock is held, and the journal's first byte is nonzero; those checks are reads through a read-only open of the journal (C15). If the journal is hot and the pager is read-only, the call fails with `SQLITE_READONLY_ROLLBACK` before any lock upgrade or playback (C14). On a writable pager the same call takes an EXCLUSIVE lock, opens the journal read-write, syncs it, plays it back into the database file, and deletes or truncates the journal (C14). The one write `hasHotJournal` can perform, deleting a stale journal beside a zero-page database, requires a RESERVED lock and is skipped when that lock is not granted (C15). So a read-only connection refuses a hot journal rather than playing it back; the refusal is a distinct extended result code the diagnostic can report.

**(d) Strategies for an offline diagnostic.** Each strategy is stated with the code condition that excludes or admits the hardened path.

- **Keep the production database in rollback-journal mode.** No `Wal` object is created unless a `-wal` file exists or the header read-version byte is 2 (C11, C12). With no `-wal` file present this excludes the hardened path entirely, and the diagnostic never touches shared memory. Residual: a stray `-wal` file next to a rollback-mode database with a nonzero page count is still opened (C11), and a hot journal on a writable connection is played back (C14); on a read-only connection it is refused (C14). This strategy also changes the production write path's concurrency and durability characteristics, which is why it is listed as a decision rather than selected here.
- **Open with `immutable=1`.** The pager treats the file as a temp file: read-only, no locks, pager state starts as reader (C16). Because the state is never "open", the hot-journal block is skipped; because the temp-file flag is set, neither `pagerOpenWalIfPresent` nor `sqlite3PagerOpenWal` opens a WAL (C11, C12, C16). This excludes the hardened path and all writes. Residual: the documented contract assumes the file cannot change even by a higher-privilege process; if another `ask` process writes during the check, results can be wrong or report `SQLITE_CORRUPT` (C17). WAL content is ignored, so the view can be stale, and a hot journal is neither played back nor reported. The owner excluded `immutable=1` for doctor against a database that may be changing.
- **Open with `SQLITE_OPEN_READONLY` alone.** Does not exclude the path. The side files are opened read-write (C4, C12), so recovery and read marks write the `-shm`; when the `-shm` is unwritable and no other process is attached, C3 and C2 put the connection on the hardened path. Adding `readonly_shm=1` makes it worse for a single-process tool: an existing `-shm` is opened read-only unconditionally and, with no other process holding the DMS lock, `SQLITE_READONLY_CANTINIT` is the normal result; a missing `-shm` is not created and the open fails with `SQLITE_CANTOPEN` (C3, C4). That is the reporter's reproduction configuration.
- **Open normally with a writable `-shm` and accept that recovery may write.** A writable database open excludes the path only together with a writable `-shm`. When the read-write open of the `-shm` succeeds, the DMS lock is taken and the shared memory initialized; the read-only flag on the shm node is never set, so `SQLITE_READONLY_CANTINIT` cannot be returned (C3, C4). When an existing `-shm` is not writable by the process, the open falls back to read-only regardless of the database open flags, and with no other process holding a DMS lock the connection is on the hardened path exactly as with `SQLITE_OPEN_READONLY` (C4, C3, C2). Residual: WAL recovery writes the `-shm`, a hot journal is played back into the database file and the journal deleted (C14), and close may checkpoint (C18). None of these is side-effect-free, and the diagnostic's write would be indistinguishable from an ordinary connection's.
- **Do not open through SQLite.** Inspect only file presence, permissions, and the 100-byte header: the magic string, the page size at offset 16, and the read and write version bytes at offsets 18 and 19. No pager or WAL code runs, so the hardened path and every write are excluded by construction. Residual: no schema, integrity, or content validation, and no report on WAL content, journal hotness, or lock state beyond file existence.

Strategies that exclude the hardened path on cited conditions: rollback-journal mode with no `-wal` file present, `immutable=1`, a writable open together with a writable `-shm`, and not opening through SQLite. Strategies that do not: `SQLITE_OPEN_READONLY` alone, and `SQLITE_OPEN_READONLY` with `readonly_shm=1`. Only `immutable=1` and not opening through SQLite exclude both the path and every write; each pays for that with the residual listed above.

On 2026-09-10 the owner reaffirmed strictly side-effect-free `ask doctor`, excluded `immutable=1` against a database that may be changing, and left production journal mode as an implementation choice constrained by that diagnostic contract. From the evidence above, the strategies still admissible for doctor are header-and-file inspection without opening through SQLite, and any SQLite open that the cited conditions show performs no write and cannot reach the hardened path. The repository must establish those conditions for the chosen implementation. Doctor may report that deeper validation could not safely run rather than claiming the store is healthy. The repository chooses and documents production journal mode from expected concurrency and startup cost, not solely to avoid this diagnostic edge case.

## Proposed native monitoring and verification migration

Do not build the following now. It is a proposal for owner approval and is not a prerequisite for query-input or storage work.

Native monitoring should extend the existing nightly dependency check rather than add a parallel system. Alongside the current `cargo deny` advisory and Rust dependency-freshness checks, the nightly should track SQLite release and maintenance check-ins and security announcements, and record the locked crate versions, the native source id, the enabled compile options, and the last triaged check-in. A new upstream SQLite version creates a triage item, not an automatic failure or upgrade. For each relevant fix, the triage item records affected-version ancestry, the actual trigger, compiled-feature and workload reachability, integrity or correctness impact, disposition, owner, and a review deadline, and revisits accepted exclusions when SQL, open flags, VFS, or Rust features change. Absence of a Rust advisory is not native clearance.

After adoption, the useful probes should move into the standard verification entrypoint rather than remaining a separate permanent gate. The transaction, rollback, reopen, busy, and isolation checks should become ordinary integration tests against the production storage boundary so `just verify` and `just verify-full` run them; native version and source-id checks and release-linkage checks belong in the full gate against the real release artifact; a differential damaged-file check like this record's probe belongs with them so a future version regression is caught. Once these are covered, retire the separate `sqlite-readiness` workflow, the isolated probe workspace, and the standalone scripts rather than keeping a permanent parallel gate.
