## Candidate and current releases

The preferred candidate is unchanged: `rusqlite = { version = "=0.40.2", default-features = false, features = ["bundled"] }`, with `libsqlite3-sys` 0.38.2 retained by the dedicated lockfile. Fresh [rusqlite](https://index.crates.io/ru/sq/rusqlite) and [sys](https://index.crates.io/li/bs/libsqlite3-sys) registry index downloads on September 10 UTC list these as their highest non-yanked stable versions. No newer candidate was substituted. The direct rusqlite requirement does not by itself freeze sys; adoption would require the reviewed transitive resolution in the production lockfile.

[SQLite's current release history](https://sqlite.org/changes.html) still lists 3.53.4 (2026-07-24), following 3.53.3 (2026-06-26). The candidate contains 3.53.2 (2026-06-03). Registry archives match their exact index SHA-256 checksums. The bundled `sqlite3.c`, `sqlite3.h`, and `sqlite3ext.h` are byte-identical to SQLite's [official 3.53.2 amalgamation archive](https://sqlite.org/2026/sqlite-amalgamation-3530200.zip). The C file also matches the SHA3-256 published in the [3.53.2 release history](https://sqlite.org/changes.html#version_3_53_2), independently of the ZIP hash. The ZIP, headers, registry index and GitHub archive remain HTTPS-source observations, not signed publisher attestations. This establishes which native code is present; it does not establish that its subsequent fixes are unnecessary.

Every returned entry has an upstream summary and a separately labeled applicability inference in [post-bundle-fixes.json](evidence/sqlite-readiness-2026-09-09/post-bundle-fixes.json). Assessment: the patch gap remains material and unresolved for adoption. Some fixes are outside the selected build; others affect compiled core and optional SQL capabilities. A pass of this probe or the historical RustSec check cannot turn the latter into an accepted risk. Waiting for an upstream bundle update avoids choosing an exception now; accepting this exact bundle's known gap is an explicit owner choice. Patching the amalgamation, selecting system SQLite, or switching libraries would require a new candidate review and is not proposed as an automatic fallback.

## Probe and four-target execution

The dedicated [probe](../../probes/sqlite-readiness/Cargo.toml) is an independent workspace with its own lockfile copied from the historical minimal smoke, changing only its local package name. It adds no production dependency. The [runner](../../scripts/sqlite-readiness.py) copies it into a fresh temporary workspace and target directory, checks exact pins and Rust 1.97.1, runs rustfmt and Clippy with warnings denied, builds with `--locked --release --target`, and executes native file tests. A native runner is required; cross-compilation alone cannot pass.

For both DELETE and WAL, the probe commits bound data, explicitly rolls back one transaction, rolls another back by dropping it, closes/reopens and checks the exact committed value, then holds an uncommitted write while a separate process reads committed data and attempts an immediate write transaction. The contender must receive `SQLITE_BUSY` after a configured 200 ms timeout (at least 150 ms observed), signals the parent, and waits for a handshake. After parent rollback it retries successfully. Both records are checked after reopen and `integrity_check` must return `ok`. These journal modes and timeout values are test fixtures, not application policy. The runner imposes a 30-second execution timeout.

The probe asserts the exact SQLite version and source ID and reports native compile options. Release linkage checks require a defined `sqlite3_libversion` symbol in the executable and reject a dynamic SQLite dependency using ELF `NEEDED` entries on Linux or `otool -L` on macOS. Retained evidence includes library basenames and binary/lock hashes. This checks the probe artifact, not the production release binary, oldest supported OS, glibc floor, macOS deployment floor, or universal packaging.

## Outstanding owner choices and limits

1. Accept the unchanged rusqlite/sys bundled candidate with the documented native patch gap and compiled C capabilities, or defer adoption until a reviewed bundle update. Acceptance includes native extension-loading code: the Rust load-extension feature remains off and the probe never enables or invokes extension loading. The [September 6 native-surface review](sqlite-dependency-assessment.md#build-and-native-surface) already distinguished those boundaries. There is no newer registry candidate requiring a comparison on September 10 UTC.
2. Accept registry integrity plus complete payload correspondence with the stated unsigned/publisher-authentication limits, or require additional independently verifiable publisher evidence before adoption.
3. Authorize dependency adoption separately after reviewing the four passing target results and resolving the patch/provenance boundaries. A successful matrix does not authorize adoption or establish storage readiness.
4. Before storage implementation, resolve retention/deletion across history and statistics, provider-target identity under configuration changes, partial/failed query recording, and atomicity between related records. Storage design must also define connection ownership and async blocking boundaries, file layout, schema/migrations/versioning/downgrade behavior, journal/busy policy, and side-effect-free offline doctor validation. None is selected here.

The probe does not test process-kill/power-loss durability, disk-full/permission failure, malformed database recovery, multi-database atomicity, migrations, cancellation, application latency, provider streaming, or the continue/recall/diagnose proofs. A fresh `cargo deny --manifest-path probes/sqlite-readiness/Cargo.toml --config deny.toml --locked check` passed advisories, bans, licenses, and sources under the unchanged repository policy. The first run identified missing license metadata on the local probe package; declaring the repository's Apache-2.0 license resolved that finding without changing dependencies or policy. This advisory result does not close the native patch gap. There is no new product decision or proposed mental-model edit: the repository still has assessment evidence while SQLite adoption remains pending.
